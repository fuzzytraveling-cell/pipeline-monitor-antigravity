# LESSONS —— 為什麼要寫成這樣

> 每一條都是**真的踩到過**的，不是假想。門檻是能回答
> **「下次什麼情況會再犯？」**——答不出來的不要寫進來。
>
> ⚠️ 這份會一直長。找東西**先搜關鍵字**，不要從頭讀。

## L1　`import.meta.url` 是編碼過的，`process.argv[1]` 不是

**2026-09-09 · status.mjs · 症狀：零輸出、零錯誤、離開碼 0**

判斷「這支檔案是不是被直接執行」時寫成：

```js
if (import.meta.url === `file://${process.argv[1]}`)   // ❌
```

使用者的路徑是 `/Users/…/TutorPod AI/…`——**有一個空白**。
`import.meta.url` 會把它編成 `%20`，`argv[1]` 不會。兩邊永遠不相等，
於是 `main()` 從來沒被呼叫過，而程式**安靜地正常結束**。

```js
if (fileURLToPath(import.meta.url) === process.argv[1])  // ✅
```

**下次什麼情況會再犯**：任何比對 `file://` URL 與檔案路徑的地方。
路徑有空白、中文、`#`、`?` 都會踩到，而且**症狀永遠是「什麼都沒發生」**——
不是錯誤，所以你會先去懷疑別的地方。

⚠️ 這是 R1 的形狀，發生在一個專門用來抓 R1 的工具身上。

## L2　`git diff` 看不到還沒被追蹤的新檔案　`已發生 2 次`

**2026-09-09 改動計數 · 2026-09-10 還原點比對**

`git diff --name-only` 只列**已被 git 追蹤**的檔案。新建的檔案完全不在裡面。

第一次：實際改了 4 個檔案，畫面說 **2 個**。
第二次：印出「之後有 **2** 個檔案被改過 / 其中 **3** 個還沒存進保險箱」——
**3 大於 2，算術對不起來。**

```sh
git diff --name-only            # 只有已追蹤的
git ls-files --others --exclude-standard   # 這個才是新檔案
```

**下次什麼情況會再犯**：任何「數這次動了幾個檔案」的地方。
⚠️ 而且**漏掉的方向固定是讓改動看起來比較小**——那是危險的那一邊，
因為它讓人以為安全。**AI 生成最常見的產物就是新檔案。**

⚠️ 另外：**一個算術對不起來的儀表板，使用者不會再信它第二次。**
`3 > 2` 一眼就看得出來，而那一眼會毀掉整個工具的可信度。

## L3　感測器有一個「開始的日期」，而畫面說了謊

**2026-09-10 · 五關顯示**

`/spec` 那天稍早**真的跑過**，但感測器是之後才裝的。
畫面理直氣壯寫著 **「A 沒跑過」**。

那是 **R1**：把「沒問到」編碼成「答案是沒有」。

修法不是加註解，是改文案：**「沒有紀錄」**，並固定附一句
「感測器從 X 才開始記，在那之前發生的事情它一輩子都不會知道」。

**下次什麼情況會再犯**：任何「從紀錄推論事實」的地方。
**紀錄的起點不等於世界的起點。** 保留期限（三個月）到期丟掉的資料同理——
問到更早的期間要回答「超過保留期限」，不是「沒跑過」。

## L4　`--git-common-dir` 在一般 repo 回相對路徑，worktree 才回絕對路徑

**2026-09-09 · 專案名稱顯示成 `.`**

```
一般 repo   → .git                     （相對！）
worktree    → /abs/path/to/repo/.git   （絕對）
```

直接拿去 `basename(dirname(...))` 在一般 repo 會得到 `.`。
先判斷是不是 `/` 開頭，不是就跟 `--show-toplevel` 接起來。

**下次什麼情況會再犯**：任何拿 git 的路徑輸出去算東西的地方。
⚠️ 這也是為什麼要用它——**它是唯一能讓三個 worktree 認出「我們是同一個專案」的東西。**

## L5　靠 diff 的文字排版判斷語意，會安靜地失效

**2026-09-09 · 相依偵測**

原本用 `^\+\s*"[^"]+":\s*"[\^~]?\d` 去 diff 裡撈新增的相依。
那**假設 `package.json` 是一行一個相依**。壓成一行的就完全撈不到——
而且是安靜地撈不到，回報「新增 0 個」。

改成**解析兩個版本的 JSON、取鍵的差集**。精確，而且跟排版無關。

**下次什麼情況會再犯**：任何用正則去讀結構化資料的地方。
**有 parser 就用 parser。**

## L6　樣本太少的統計，長得跟有依據的基準一模一樣

**2026-09-09 · 改動規模比例尺**

只有 2 個 commit 的時候，「這個專案平常 5 個檔案，最多到過 5 個」照樣印出來。
數字是真的，但**它什麼都沒告訴你**，卻長得像一個可以拿來比較的基準。

現在樣本 < 5 就不給比例尺。

**下次什麼情況會再犯**：任何從歷史算平均／中位數的地方。
**寧可不給，也不要給一個看起來有依據的雜訊**——這是 R3。

## L7　`null` 漏到畫面上

**2026-09-09 · 零 commit 的 repo 顯示 `━━ empty · null ━━`**

一個 commit 都沒有時 `git rev-parse --abbrev-ref HEAD` 會失敗，
我們的 `git()` 回 `null`，然後那個 `null` 直接被印出來。

`symbolic-ref --short HEAD` 在零 commit 時仍然答得出來，拿它當備援，
再退回 `(還沒有分支)`。

**下次什麼情況會再犯**：任何把 `git()` 的回傳值直接放進字串的地方。
⚠️ **讀的人不是工程師**——`null` 對他來說不是「查不到」，是一個看不懂的錯誤。

## L8　用 Bash 寫檔案會完全繞過 hook

**2026-09-10 · AC-10 的盲區**

hook 的 matcher 只認 `Edit`／`Write`／`NotebookEdit`。
用 Bash heredoc、`sed`、`python` 寫檔案**一筆都不會被記到**。

所以定了一條規則：**檔案數量一律由 git 算，不准用 hook 的紀錄算。**
hook 的檔案紀錄只用來做 git 做不到的那一件事：**把檔案連回「當初說了什麼」**。

**下次什麼情況會再犯**：任何想從 hook 紀錄推論「總共動了什麼」的地方。
**hook 看得到的是它被掛上的那幾個工具，不是全世界。**

## L9　同一份文件抄第二次，就是第二個真相來源

**2026-09-10 · 決定不建 FAILURE-PATTERNS.md**

盤點時發現想寫進去的東西，`CLAUDE.md`（紅線）、本檔（實例）、
規格的 AC 三個地方都已經有了。再開一份就是第三次抄寫。

**判準**：建新文件之前先問——
**「它有沒有獨佔的內容？」** 和 **「它過期的時候，什麼東西會變紅？」**
兩題都答不出來就不要建。

⚠️ 什麼時候才該建 `FAILURE-PATTERNS.md`：**同一類錯誤犯第二次**的時候
（L2 已經達標），而且**要連「把它推到眼前」的機制一起建**。
一份沒有觸發機制的模式清單，是一個沒人會打開的檔案。

## L10　檢查要抓「意圖」，不要抓「字面」——否則 CI 會變成狼來了

**2026-09-10 · CI 的「不准依賴 TutorPod」規則**

`CLAUDE.md` 寫了「不准依賴 TutorPod」，於是 CI 加了一條 grep。
**第一次跑就 4 個誤報，全部是註解**——而且是「解釋為什麼這樣做」的註解，
正是 `CLAUDE.md` 自己要求要寫的那種。

> 註解**提到** TutorPod，跟程式碼**依賴** TutorPod，是兩件事。
> 一條會為了正當的東西變紅的檢查，第三次之後就沒有人看了——**那時它等於不存在。**

修法是把註解行排除，不是把註解刪掉。

**下次什麼情況會再犯**：任何用 grep／正則去執行一條「規則」的地方。
先問：**這條檢查抓到的東西，跟我真正想禁止的事情是同一件嗎？**
⚠️ 這跟 `status.mjs` 不准自己編門檻是同一個道理——
**會亂叫的工具沒有用，不管它叫得多有道理。**

## L11　「沒有基準就拿自己當基準」，永遠回報「沒有變化」

**2026-09-10 · 相依偵測 · 測試抓到的（手動測試兩天沒抓到）**

```js
const depsBefore = since ? readDeps(git(['show', `${since}:package.json`])) : depsNow;  // ❌
```

沒有還原點的時候 `depsBefore === depsNow`，差集永遠是空集合。
**新增的相依一輩子不會被報出來**——而畫面上「新增相依：0 個」
跟「真的沒有新增相依」長得**一模一樣**。

正確的基準是 `HEAD`（＝還沒 commit 的東西），不是工作區自己：

```js
const depsBefore = readDeps(git(['show', `${since ?? 'HEAD'}:package.json`]));  // ✅
```

**下次什麼情況會再犯**：任何「跟之前比」的功能，在**「之前」不存在**的時候。
先問：**基準缺席的時候，我拿什麼當基準？** 拿自己當基準＝永遠沒有差異＝
一句永遠成立的假話。這是 R1 的另一個身體。

⚠️ **這一條是這個專案第一個「只有測試抓得到」的 bug。**
它不會當機、不會報錯、畫面看起來完全正常——我手動測了兩天都沒發現。

## L12　寫出資料的程式碼、跟 `.gitignore` 那一行，是同一個決定的兩半

**2026-09-10 · 感測器紀錄被 commit 並推上 GitHub**

`.gitignore` 寫了 `checkpoints/`，**漏了 `logs/`**。
而 `logs/` 裡是使用者打的**每一則訊息前 200 字、對話標題、專案路徑**。
推上 GitHub 之後才發現。

⚠️ **這種錯沒有任何徵兆**：git 不抱怨、測試不紅、功能完全正常。
跟 L1（路徑有空白就靜默失效）、L11（拿自己當基準）是同一族——
**都是「看起來一切正常」的失敗**。

**修法不是「下次小心」**，是 `scripts/privacy.test.mjs`：
維護一份「程式自己會寫出來的資料夾」清單，斷言它們
**既沒有被追蹤、也確實有寫進 `.gitignore`**。

**下次什麼情況會再犯**：任何新增「會寫檔到專案資料夾」的功能時。
⚠️ 加了會寫檔的程式碼，就要同步加進 `MUST_NEVER_BE_TRACKED` 那份清單——
**只做前一半，私人資料就上去了。**

> 這跟 `CLAUDE.md` 的「新增 docs 檔必須同步改索引」是同一個形狀：
> **兩個動作其實是一個決定，而工具只會提醒你做了一半的那一種。**
