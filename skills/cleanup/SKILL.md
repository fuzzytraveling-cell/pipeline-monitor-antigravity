# C —— 打掃（通用版）

你現在是**收尾清場的人，不是設計師**。

打掃是把施工留下的鷹架拆掉，**不是重畫設計圖**。後者可能更好，但那是另一件事，要回去找 A 重新畫。

> ⚠️ **這一關沒有需求規格。** 你的輸入只有「這段看起來可以更簡潔」——**那是品味，不是規格。**
> 品味沒有失敗條件，所以這一關是五關裡最容易自己變成 bug 來源的一關。下面每一條規則都是為此存在的。

這一支裝在使用者層級，任何專案都叫得到，所以它**不知道你這個專案的任何事**——
哪些程式碼看起來多餘、其實是刻意的，只有那個專案自己的手冊知道。

## 產出什麼、不產出什麼

**產出**：
- 只做**證明得出來是死的**的刪除（判準見下）。
- 其餘全部寫進「只建議、沒動手」清單。
- 一份三段式報告：已改／只建議／因為規則放過的。

**不產出**：
- 不改控制流、不抽新模組、不跨檔案搬東西、不改函式簽名、不合併錯誤分支。
- 不碰測試檔（唯讀）。
- 不碰逾時、重試、fallback、快取、守衛常數（見「絕對不碰」）。
- 不新增功能；不宣稱「更乾淨了所以更好」——你能證明的只有「刪掉的東西是死的」。

## 專案專屬的東西從哪裡來

| 要知道的 | 去哪讀 | 沒有的話 |
|---|---|---|
| 進場與收工要跑哪些檢查 | `package.json` 的 `scripts`：`lint`、`test`、`test:unit`、`build` 有哪些就跑哪些（跟 `pipeline-status --checkpoint` 同一條規則） | 沒有任何檢查可跑 → 明說「沒有東西能證明我沒弄壞」；只准做 lint 級的靜態證明（沒用到的 import、整段註解掉的），其餘全進建議清單 |
| 哪些是測試檔（唯讀） | 路徑含 `test`、`spec`、`__tests__` 的檔案；測試設定檔（`vitest.config.*`、`jest.config.*`、`tests/setup.*` 之類） | 沒有測試 → 同上一格 |
| 刻意的決定（看起來像該清、其實不能動） | `CLAUDE.md` 裡任何寫著「刻意」「不是 bug」「不要順手修」的段落 | 沒有就沒有；但下面的「絕對不碰」照樣適用 |
| 這個專案犯過的錯 | `docs/FAILURE-PATTERNS.md`、`docs/LESSONS.md` | 用三條通用判準：R1 沒問到≠沒有、R2 跑過≠通過、R3 不編數字 |
| 讀報告的人是誰 | `README.md`、`CLAUDE.md` | 當成不是工程師來寫 |

## 範圍

只看**這一輪動到的檔案**：
- 有參數 → `git diff $ARGUMENTS --name-only`
- 沒參數 → `git diff HEAD --name-only` **加上** `git ls-files --others --exclude-standard`（新檔案 `git diff` 看不到）

不要去打掃這一輪沒動到的地方——那是另一件事，要另外開一輪。

## 進場條件

先跑一次專案有的檢查（上表第一格）。**任何一項不綠 → 立刻停手回報，不要「順手一起修掉」。**
在紅的地基上打掃，之後測試變綠變紅都分不清是誰造成的。

⚠️ 紅有兩種：**跑了沒過**，跟**根本沒跑起來**（指令找不到、工具沒裝）。分開講，不要把「沒跑」講成「沒過」。

## 絕對不碰

1. **測試檔——唯讀。** 測試是唯一能證明「我沒弄壞東西」的東西。打掃的人可以順手改它，那個證明就不算數了——
   就像讓考生自己改答案卡。覺得某個測試寫得囉唆？停手回報，由人決定。
2. **錯誤分支、逾時、重試、退避、fallback。** 三個 `catch` 看起來一模一樣，你的本能會說「合併」。
   但三個不同的原因，使用者要做的下一步可能是三件不同的事——**原因的數量要等於「下一步不同」的數量。**
   併成一句「發生錯誤」，等於把他的下一步刪掉了。
3. **存在理由是「讓它變快」的程式碼。** 註解或命名含快取、預存、批次、debounce、預熱、prefetch 的一律不碰。
   拿掉它測試照樣綠，症狀幾天後才在使用者那邊出現。
4. **上限、守衛常數、`?.`、預設值。** 看起來「沒人用到」的常數往往是唯一的護欄；
   「這裡不可能是 undefined」是錯的，舊資料就是會缺欄位。

## 判準：證明得出來才動手

**「刪掉之後測試還是綠的」不是安全訊號，是沒有資訊。**

| 刪掉之後 | 代表什麼 |
|---|---|
| 測試**變紅** | 這段是有用的 → 不准刪，也不准改測試 |
| 測試**還是綠** | 可能真的沒用／可能有用但沒人在測——**你分不出是哪一個** |

所以判準是**能不能靜態證明它是死的**，不是「有沒有測試」。

**✅ 證明得出來 → 動手**
- 沒用到的 `import`／區域變數——lint 直接證明
- 整段被註解掉的死碼——看得見
- 模組內私有、而且全檔搜尋零呼叫點的函式——搜得出來
- **同一個檔案內**字面重複的區塊——對得出來

**❌ 證明不出來 → 只寫進建議清單**
- 任何**跨檔案**的東西
- 任何需要推理才能說「多餘」的判斷
- 任何用字串或動態方式取用的東西

⚠️ 預期會有很多項落在建議清單。**那是正確的結果，不是失敗。**

## 收工檢查

1. **同一組**檢查再跑一次，必須依然全綠。回報時說是哪幾個指令、結果如何；沒跑的說沒跑。
2. 這次動到的檔案（`git status --short`，**新檔案也算**）不得出現任何測試檔。出現就是違規，**整輪作廢**。
3. 改到程式區的話，提醒使用者：這次的改動該給 D 魔鬼教官看一次（`/pipeline-monitor:chaos-check`）。

## 輸出格式

先一行結論（做了幾項、建議幾項、放過幾項），然後三段：

```
## 已改（每一項都要能回答「怎麼證明它是死的」）
- <檔案:行號> —— <改了什麼> —— <證據：lint 報沒用到／搜尋零呼叫點／整段被註解掉>

## 只建議、沒動手（證明不出來的）
- <檔案:行號>
  白話：<這段程式在做什麼，用這個專案的使用者的世界比喻>
  會發生的情況：<誰、什麼時候、在畫面上看到什麼>
  不修會怎樣：<現在沒壞就老實說「現在沒壞，風險是…」，不要把還沒發生的事講得像正在發生>
  要驗證的話：<該怎麼做>

## 因為規則放過的（踩到刻意的決定、踩到禁區）
- <檔案:行號> —— <是哪一條規則>
```

最後那段比「我改了什麼」更有價值——它告訴人這些規則正在生效。

🔴 **每一項建議都白話在前、技術在後。** 讀報告的人可能不是工程師；純技術陳述（「fallback 路徑」「抽新模組」「no-unused-vars」）
他無法判斷該不該做，那清單就只是寫給自己看的。判準：**他讀完能不能自己判斷這一項該做、該押後、還是該直接丟掉？**

## 邊界

- 想做「不產出」那一欄的事 → 退回給 A 重寫規格，不要在這一關做。
- 這一關是選配：不進 CI、不是 commit 的前置條件、不自動觸發。打掃沒做，只是亂，東西照樣能用。
- 專案自己也有 `/cleanup` → 兩個並存，使用者叫哪個就跑哪個。產線監視器把兩種名字都算成 C 這一關。
